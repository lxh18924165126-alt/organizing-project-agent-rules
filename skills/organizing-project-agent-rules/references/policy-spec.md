## 1. 修改授权与连续执行

- 用户使用明确的修改性表达时，视为授权在当前任务范围内连续实施，包括 R1、R2 和 R3。
- “直接开始”不是授权的必要条件，只表示减少实施前说明。
- “只分析”“只审查”“先给方案”“暂时不要修改”等明确只读限制优先。
- 授权覆盖完成目标合理必需的代码和规则调整，但不自动扩大为未要求的生产操作、部署、外部不可逆影响或无关重构。
- 本 Skill 自身只改规则文档；上述授权模型是它需要写入项目根规则的项目执行约定。

## 2. 风险优先，数量只作为升级信号

- `R1`：局部、可逆，不改变公共契约、持久化数据、安全边界或基础设施。直接实施并做最低验证。
- `R2`：跨领域、共享契约、依赖、构建、CI、基础设施，或需要多组集成验证。生成简短微计划后直接实施；微计划不是计划模式，也不需要用户批准。
- `R3`：迁移、数据丢失风险、认证权限、安全、生产、不可逆或破坏性兼容变更。明确修改请求本身即授权当前范围内的 R3 实施；进行风险分析和强化验证，但不设置重复确认点。
- 超过 3 个职责领域、包、服务或可部署组件，或预计超过 100 行手写代码，只触发重新评估，不自动进入复杂工作流。
- 生成代码、锁文件、格式化和快照变化不直接计入手写代码规模，但其影响仍需评估。

## 3. 方案外新增 R3 的安全默认

实施中发现原方案未包含的新 R3 时：

1. 优先保护数据；
2. 优先保持兼容；
3. 优先可逆、分阶段和最小外部影响；
4. 可以增加兼容层、dry-run、回滚路径或把危险动作实现为默认不执行的脚本；
5. 不自动执行新增的数据删除、生产操作、破坏性公共契约删除、降低安全保护或其他外部不可逆动作；
6. 完成其余安全部分，并在最终结果中说明推迟的危险步骤；
7. 只有无法获得任何正确且可验证的安全结果时才视为硬阻断。

## 4. 路由机制

- 同时依据用户目标、预计或实际文件路径、实际影响边界进行路由。
- 任务开始时初始路由；调查和实施过程中进入新领域时增量加载。
- 多个条件命中时读取规则并集，不读取无关规则。
- 路径是证据，不是唯一判断；只读查看某目录不必自动加载该领域完整规则，除非它影响决策。
- 常见领域包括但不限于：前端、后端、公共契约、数据库、安全、基础设施、架构。

## 5. 文档与检查点

- 修改公共行为、API、配置、部署方式、数据格式或架构边界时，同步更新对应文档。
- 检查点默认是 Agent 内部自检，不是用户审批点。
- 除真正硬阻断外，不因到达检查点而中断连续执行。
- 不为满足流程形式创建与任务无关的设计、计划、日志或报告。

## 6. 验证

- 所有修改都必须检查最终 diff，并运行最窄且直接相关的测试、类型检查、构建、lint、配置校验或文档检查。
- R2、R3、Harness 或局部验证暴露更大影响面时，加载强化验证规则。
- R2 验证所有受影响领域及其直接集成边界。
- R3 额外验证兼容性、数据、安全边界和恢复路径。
- 验证失败后优先修复并重新运行。
- 未运行的检查不得声称通过；不得无证据宣称完成。

## 7. 可选工作流

### AgentHub

- 默认关闭，只有用户明确要求多 Agent、Agent 分工、并行代理，或已批准任务明确包含多 Agent 时才加载。
- R2、R3、任务复杂、计划、Harness 或“适合并行”都不能自动启用。
- 启用后按任务歧义、失败成本、责任和整合难度选择 Agent 数量、角色、模型和推理强度，而不是只按代码行数。
- 优先并行只读调查、测试分析和审查；写入任务必须隔离所有权。
- 主 Agent 是唯一最终集成者，并负责检查实际 diff 和最终验证。
- 用户要求多 Agent 不代表必须创建尽可能多的 Agent。

### Harness

- 默认关闭，只有用户明确且无歧义地要求 Harness、工程化设计、工程化实施或工程化工作流时才加载。
- R2、R3、计划、AgentHub、完整验证或任务复杂都不能自动启用。
- Harness 可以独立启动；有批准计划时消费计划，没有计划但目标明确时建立轻量内部工作包并直接实施。
- Harness 检查点是内部自检，不是默认审批点。
- Harness 不自动启用 AgentHub，不自动加载全部 Superpower，不强制为短任务生成大量持久化文档。

### Superpower default-deny policy

Superpower 默认禁止。优先级为：

`explicit no-superpower > allowed gates > default deny`

只有满足以下一个授权门，才允许进一步考虑具体技能：

1. 当前任务是实际修改仓库的任务，并已按项目既有风险规则真实判断为 R3；
2. 用户明确且无歧义地要求工程化设计、工程化实施或工程化工作流，包括“使用工程化设计”“以工程化方式设计/实施”“使用工程化工作流”“使用 Harness”“按 Harness 实施”或显式调用项目约定的 `$harness`。

“认真完成”“完整/高质量/生产级实现”“仔细设计”“任务复杂”等质量或规模措辞不构成第二个授权门。R0、R1、R2、跨领域、计划模式、先制定计划、多 Agent、AgentHub、根因未知、调试困难、修复失败、验证失败、完整测试、代码审查、TDD、点名 systematic debugging、点名任一 Superpower Skill 或已有详细计划，也都不能独立解除禁令。

R3 必须依据数据迁移/丢失、认证授权、隐私安全、生产、不可逆操作、破坏性公共契约、重大兼容或高权限基础设施等真实风险判断；不得因复杂、耗时、文件多或跨模块而升级。只读分析即使讨论高风险主题，也不是 R3 修改。

满足授权门只解除禁令，不代表必须使用。先判断项目普通规则、领域规则和验证规则是否足够，是否会重复流程，以及是否有职责更窄、更轻量的方式；能可靠完成时不使用 Superpower。R3 不自动加载技能，Harness 不自动调用技能链。

允许时仍遵守最小调用：

- `using-superpowers` 总入口始终禁止；不加载全部 Superpower；
- 每次只考虑当前阶段职责最窄的具体技能，后续技能重新独立判断，不因一个技能自动串联其他技能；
- 不运行与项目工作流重复的完整流程，不覆盖项目风险、架构、领域或验证规则；
- 用户明确禁止 Superpower 时，即使 R3 或显式 Harness 命中也不得使用。

迁移旧规则时，不静默删除“复杂故障直接触发 systematic-debugging”“单独要求 TDD 触发 test-driven-development”“计划模式、R2、验证失败、Harness 或点名技能自动触发”等宽松规则。逐条记录原文、原位置、与本政策的冲突和新权威位置，状态使用 `superseded-by-current-user-policy`。

不在项目规则中管理 Codex 计划模式；用户会自行切换，计划模式本身不构成 Superpower 授权门。

## 8. 规则优先级

固定优先级为：

```text
平台、沙箱、命令规则和 CI 硬约束
> 用户当前明确的目标、范围和禁止事项
> 根 AGENTS.md 的始终有效内核
> 架构、安全和数据不变量
> 命中的具体领域规则
> AgentHub、Harness、Superpower 等可选工作流
> 仓库现有惯例
```

- 工作流只能决定如何执行，不能覆盖上层约束。
- 同层冲突时采用职责更具体且更安全的规则。
- 现有代码惯例只在没有明确规则时作为默认。
- 用户明确要求改变某个架构护栏时，应把“修改该护栏”视为任务目标，而不是假装护栏不存在。

## 9. 根文件必须保留的项目属性

以下内容必须在根 `AGENTS.md` 中有简洁、项目特定且可执行的结论：

- 基本约定；
- 项目背景；
- 风险与改动规模判断；
- 技术栈说明与文档索引；
- 文档与检查点；
- 最低验证；
- 禁止事项；
- 核心架构护栏；
- 领域规则和可选工作流的触发入口；
- 规则优先级。

领域编码细节、长检查清单、例子、设计理由和工作流全过程必须下沉。

## 10. 运行时配置边界与 AgentHub 治理

### 操作者运行时配置

- `~/.codex/config.toml`、`$CODEX_HOME/*.config.toml`、`model_context_window`、`model_auto_compact_token_limit`，以及当前模型、推理强度、账户和价格阈值属于用户/机器运行时配置。
- 本 Skill 默认不得读取、备份或修改用户配置；不得把它们放入根或运行时路由规则，也不硬编码 `272000`、`240000`、`258400` 或价格倍率。当前模型/价格建议必须先核对官方文档，并作为操作者建议而非项目规则。
- 旧内容分类为 `operator-runtime-config`，状态为 `externalized-runtime-config`；在非运行时迁移/操作记录保留原文、来源、目标和“不自动应用”说明。盘点只扫描仓库，校验只检查根与当前直接路由叶子。

### AgentHub 能力层级与回退

- 根只保留 1～2 行显式触发；R3、直接开始、复杂度和修改规模不自动启用。完整规则放在 `docs/agent/workflows/agenthub.md` 或等价叶子。
- 深度/关键能力层级用于高歧义、架构、安全、迁移、集成和审查，当前可映射 Sol high/xhigh，max 仅用于最困难任务；均衡实现能力层级用于代码、测试、重构和缺陷，当前可映射 Terra medium/high；快速确定性能力层级用于日志、扫描、提取和机械转换，当前可映射 Luna low/medium。
- 按歧义、失败成本、推理、集成和验证需要选择最低可靠能力，而不是代码行数。模型名只是当前映射；不可用时回退到最近可用能力并报告，不使用 `ROUTING_HOLD`。仅用户明确要求某个不可替代模型且确认不可用时阻断。
- 不依赖 `rollout.model`、`rollout.effort`、`parent_thread_id`、强制旧线程/fork/checkpoint，不编造运行时元数据，也不声称项目规则能切换主线程模型。
- `.codex/agents/*.toml` 仅在项目已使用 AgentHub 或用户明确要求时作为可选实现层，默认不创建或修改；用户 profile 不是项目规则。

### 权限、写入与删除

- Explorer、Reviewer、Advisor 和只读验证角色保持 read-only；Worker 仅在所有权内 `workspace-write`。`danger-full-access` 需要当前任务的单独明确用户授权且平台允许；R3、普通修改和直接开始都不授权它。子 Agent 不扩大权限，不默认读取密钥。
- 未经明确要求，不 commit、push、publish、deploy 或执行生产操作。
- 共享工作区默认单写者；并行写入只在显式 AgentHub、隔离 worktree/仓库、不重叠可写根和明确所有权下使用。共享契约、schema、锁文件、全局配置只有一个所有者；唯一 Integrator 负责最终集成、实际 diff 与验证，发现重叠即停止并行写入。
- 明确修改、重构、迁移或清理中合理必要的范围内仓库文件删除是允许的；不得删除无关、仓库外、生产、用户主目录或系统内容，新发现的破坏性删除采用安全默认。不要写“一律禁止并行写入”或“一律禁止删除任何文件”，应写隔离、所有权和范围边界。

## 11. 模式、证据与幂等

- `bootstrap`、`migrate`、`repair`、`audit` 只改变内部执行入口；共享本文件的风险、预算、路由、冲突优先级、验证和可选工作流政策。
- 证据优先级固定为：用户当前明确信息 > 现有 `AGENTS.md`/明确规则文档 > CI、lint、构建、schema 等机器强制配置 > 多个相互印证的代码/目录结构 > 单一代码模式。
- 其他助手说明是证据，不自动成为 Codex 权威规则。单一代码模式不得直接升级为项目硬规则。
- 只有无法可靠取证、会实质改变根禁止事项/架构护栏/路由且省略会导致编造时才集中询问；不重复询问已回答问题。
- bootstrap 只创建实际领域所需叶子；根只引用真实文件，默认不创建嵌套指令。
- 相同输入与用户信息必须产生稳定模式、Rule ID、路由、顺序和问题集合。validator 通过且无语义缺陷时 audit 为 no-op；第二次运行不得重复规则、迁移或无意义 diff。
